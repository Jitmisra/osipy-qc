# Batch mode — run this on your own cohort tomorrow

> *"Batch mode?"*

Yes. `osipy_qc.batch` grades a whole folder of subjects in one pass, and there is a
cohort dashboard on top of it. Every command below was run, and the output pasted,
against a synthetic cohort built from `osipy_qc/synth.py` — no command is
documented here that was not executed first.

Read [MINIMUM_INPUTS.md](MINIMUM_INPUTS.md) alongside this: batch mode grades each
subject against the same input contract, so a cohort of bare CBF maps gives you a
cohort of `coverage 1/9` reports.

---

## 0. Privacy: batch mode runs on your machine, and must

**Batch grading is entirely local.** `grade_folder()` reads NIfTIs from the path
you give it, grades them in memory, and never opens a network socket. The
dashboard is an `http.server` bound to `127.0.0.1` by default. Nothing is
uploaded, nothing is phoned home, and there is no telemetry anywhere in the
package (`numpy` + `nibabel` + the standard library; no HTTP client is imported).

**Do not put DUA-restricted cohort data into the public demo instance.** The
hosted demo at the URL in `render.yaml` is a convenience for people who want to
see what a report looks like. It runs the single-scan upload console, which writes
each upload to a temp directory and holds the last few graded scans in the
server's memory — which is fine for a synthetic map and **not** an appropriate
place for participant scans you are contractually responsible for.

This repository is its own example of the distinction:

| Path | What it is | May it be uploaded or committed? |
|---|---|---|
| `example_data/` | synthetic CBF + GM/WM/CSF, generated by `synth.py` | yes — it is committed on purpose |
| `data/` | the three real ASL datasets the mentors provided, including ADNI subject `027_S_6327` | **no.** Git-ignored (`data/*`), under a data-use agreement |
| `output/` | CBF maps derived from those scans by `oxford_asl` / ASLPrep | **no.** Git-ignored (`output/*`); a derived map is still participant data |

Derived is not de-identified: a CBF map retains the head geometry it was
reconstructed from. If your data came with a DUA, `--dashboard` on your own
machine is the right tool and the public instance is not.

## 1. Every flag, and what it actually does

From `osipy_qc/cli.py`. `--help` is reproduced faithfully; the third column is what
the code does, and disagreements are called out in §5.

| Flag | `--help` says | What the code does |
|---|---|---|
| `folder` (positional) | folder of raw NIfTIs to QC | `load_folder()` — recurses the tree, infers roles from filenames, loads the 4D ASL series. This is the **raw-data** path; it never looks for a CBF map. |
| `--json` | print the JSON report | prints `report.to_json()` **instead of** the table. Includes the `coverage` block. |
| `--demo` | run the full Stream B on synthetic data | grades one synthetic clean CBF map with `checks=None`, i.e. **the whole registry** (20 checks) — so all 9 Stream-A checks and `4.1` also run and come back `UNKNOWN`. |
| `--provenance` | print where every threshold came from, then exit | dumps 36 threshold records grouped as 11 published / 9 implementation / 16 uncalibrated, then returns. **Takes precedence over every other flag.** |
| `--html PATH` | write a self-contained visual HTML report to PATH | writes it **in addition to** the console output, and only on the `--demo` / `folder` paths. Silently ignored with `--serve`, `--dashboard`, `--dashboard-demo` or `--provenance`, because those return earlier. |
| `--population NAME` | adult or neonate (default: adult) | validated by `for_population()`, which **raises** on an unknown name. Only reached on the `--demo` / `folder` paths — see §5. |
| `--serve` | local web UI: upload a single CBF map in the browser | starts the upload console with `spa=False`, so it serves its own server-rendered HTML and never the React build. Also accepts raw acquisition files, not only a CBF map. |
| `--dashboard FOLDER` | cohort dashboard: grade every subject subfolder of FOLDER and serve it | `grade_folder(FOLDER)` then `serve_dashboard()`. Exits **2** if no subject folder contained a CBF map. Needs the React build to render — see §4. |
| `--dashboard-demo` | cohort dashboard populated with a synthetic demo cohort | `demo_cohort(14)` — a deterministic clean/borderline/garbage mix, no disk I/O. |
| `--port N` | port for the web UI (default 8000, or `$PORT`) | accurate. |
| `--host H` | interface to bind (default 127.0.0.1; use 0.0.0.0 …) | accurate. `0.0.0.0` exposes the server to your network — the package is not hardened for that. |
| `--no-browser` | do not open a browser window | accurate; applies to all three server modes. |

**Precedence**, from the order of the `if` blocks: `--provenance` →
`--dashboard-demo` / `--dashboard` → `--serve` → `--demo` / `folder`. The first
match wins and returns.

There is **no** `--strict` / `--no-strict` flag and **no** `--csv` flag. Lenient
grading and tabular output are Python-only today — §2(c) below is the CSV recipe,
and `QCConfig(strict=False)` is the lenient one.

### (b) Grade a folder of subjects

There is no CLI flag for "grade a cohort and print it", so this is the five-line
Python entry point. `grade_folder` returns a `list[Subject]`; `summarise` gives the
cohort statistics.

```python
from osipy_qc.batch import grade_folder, summarise

subjects = grade_folder("/path/to/cohort")
summary = summarise(subjects)

print(f"{summary.total} subjects: {summary.pass_rate:.0%} pass, "
      f"{summary.warn_rate:.0%} warn, {summary.fail_rate:.0%} fail")
for s in subjects:
    cov = s.report.coverage
    print(f"  {s.sid:10s} {s.overall:8s} QEI={s.qei}  "
          f"coverage {cov['graded']}/{cov['total']}  {s.primary_artifact}")
```

Run on a synthetic cohort of **eight** directories: five full subjects (CBF + GM +
WM + CSF), one with a CBF map only, one whose CBF map is all zeros, and one
containing only a GM map. Note that seven come back — the GM-only directory is
skipped silently, because it has no CBF map:

```
7 subjects: 57% pass, 0% warn, 29% fail
  sub-01     PASS     QEI=0.9695  coverage 7/7  -
  sub-02     PASS     QEI=0.9695  coverage 7/7  -
  sub-03     FAIL     QEI=0.4427  coverage 7/7  QEI
  sub-04     FAIL     QEI=0.0  coverage 7/7  QEI
  sub-05     PASS     QEI=0.9695  coverage 7/7  -
  sub-06     PASS     QEI=None  coverage 1/9  -
  sub-08     UNKNOWN  QEI=None  coverage 0/9  -
```

Two things to read carefully here.

**`sub-06` has a CBF map and no tissue maps, so it reads `PASS` at `coverage 1/9`.**
That is not the same claim as `sub-01`'s `PASS` at `7/7` — one check of nine
reached a verdict, and it was the plausibility check, not the QEI. The coverage
column is the only thing that says so. Never build a cohort table without it.

**57% + 0% + 29% ≠ 100%.** `summary.rates` only carries `PASS` / `WARN` / `FAIL`,
so an `UNKNOWN` subject — `sub-08`, whose map is all zeros, so even the
self-derived brain mask is empty — falls out of the percentages entirely. Read
`summary.counts` for the full breakdown:

```
counts: {'PASS': 4, 'FAIL': 2, 'UNKNOWN': 1}
artifacts: [('CBF level', 2), ('Negative CBF', 2), ('QEI', 2),
            ('GM/WM ratio', 1), ('SNR', 1), ('sCoV', 1)]
```

### (c) One CSV row per subject

The recipe most cohorts actually want. Saved as `grade_cohort.py`:

```python
"""Grade a cohort of CBF maps and write one CSV row per subject."""
import csv
import sys

from osipy_qc.batch import grade_folder, summarise

folder = sys.argv[1]
subjects = grade_folder(folder)
summary = summarise(subjects)

with open("cohort_qc.csv", "w", newline="") as fh:
    w = csv.writer(fh)
    w.writerow(["subject", "verdict", "graded", "total", "complete", "qei", "flag"])
    for s in subjects:
        cov = s.report.coverage
        w.writerow([s.sid, s.overall, cov["graded"], cov["total"],
                    cov["complete"], s.qei, s.primary_artifact])

print(f"{summary.total} subjects: "
      f"{summary.pass_rate:.0%} pass, {summary.warn_rate:.0%} warn, "
      f"{summary.fail_rate:.0%} fail")
for label, n in summary.artifact_breakdown:
    print(f"  {n:3d}  {label}")
```

```
$ python grade_cohort.py /path/to/cohort
7 subjects: 57% pass, 0% warn, 29% fail
    2  CBF level
    2  Negative CBF
    2  QEI
    1  GM/WM ratio
    1  SNR
    1  sCoV

$ cat cohort_qc.csv
subject,verdict,graded,total,complete,qei,flag
sub-01,PASS,7,7,True,0.9695,-
sub-02,PASS,7,7,True,0.9695,-
sub-03,FAIL,7,7,True,0.4427,QEI
sub-04,FAIL,7,7,True,0.0,QEI
sub-05,PASS,7,7,True,0.9695,-
sub-06,PASS,1,9,False,,-
sub-08,UNKNOWN,0,9,False,,-
```

`complete=False` is the column to filter on before you quote a pass rate. Both
`sub-06` and `sub-08` are `False`; only the two `FAIL`s and the three `7/7` PASSes
are fully-evidenced verdicts.

## 3. The cohort folder layout

`grade_folder()` walks the **immediate subdirectories** of the folder you name.
Each subdirectory that contains a CBF map becomes one subject, named after the
directory.

```
cohort/
  sub-01/
    cbf.nii.gz          <- required. Anything matching the patterns below.
    gm.nii.gz           <- optional, but see MINIMUM_INPUTS.md: without it you get 1/9
    wm.nii.gz
    csf.nii.gz          <- optional; derived from gm+wm when absent
  sub-02/
    ...
```

Nesting is fine — the search is recursive **within** each subject folder — so
pipeline output directories work as-is:

```
cohort/
  sub-01/
    native_space/
      perfusion_calib.nii.gz
      pvgm_inasl.nii.gz
      pvwm_inasl.nii.gz
```

### Filename patterns

`batch._find_cbf_inputs` takes the **first match, in this order**, from a recursive
glob inside the subject folder:

| Role | Patterns tried, in order |
|---|---|
| CBF | `perfusion_calib.nii*` → `*_cbf.nii*` → `*perfusion*.nii*` → `cbf*.nii*` |
| GM | `pvgm_inasl.nii*` → `*pvgm*.nii*` → `*label-GM_probseg*.nii*` → `*gm*.nii*` |
| WM | `pvwm_inasl.nii*` → `*pvwm*.nii*` → `*label-WM_probseg*.nii*` → `*wm*.nii*` |
| CSF | `*pvcsf*.nii*` → `*label-CSF_probseg*.nii*` → `*csf*.nii*` |

So `oxford_asl` output (`perfusion_calib` + `pvgm_inasl` + `pvwm_inasl`), ASLPrep
output (`*_cbf` + `*label-GM_probseg`) and hand-named `cbf/gm/wm/csf.nii.gz` all
work without renaming.

Two traps in those patterns:

* The final fallbacks are broad substrings. `*gm*.nii*` matches **any** filename
  containing `gm`, and within one pattern the alphabetically first hit wins. If a
  subject folder holds several candidates, check which one was picked
  (`Subject.inputs` holds the arrays; log the paths from `_find_cbf_inputs` if in
  doubt).
* Do **not** point `osipy-qc <folder>` (the raw-data path) at a pipeline output
  directory. That path uses a **different** and coarser vocabulary,
  `checks.schema.classify_role` (inspect it with `role_vocabulary()`), which sorts
  files into just `m0` / `asl` / `t1` / `other` and whose ASL token list contains
  the substrings `asl`, `cbf` and `perf`. So every derived map is tagged as the
  *ASL series*:

  ```
  $ python -c "from osipy_qc.checks.schema import classify_role as c; \
      print([(n, c(n)) for n in ('pvgm_inasl.nii.gz','cbf.nii.gz','perfusion_calib.nii.gz')])"
  [('pvgm_inasl.nii.gz', 'asl'), ('cbf.nii.gz', 'asl'), ('perfusion_calib.nii.gz', 'asl')]
  ```

  Use `--dashboard` or `grade_folder` for derived maps, and the positional folder
  argument only for raw acquisitions.

### What happens to an incomplete subject folder

All four cases below were run. `coverage` here is out of 9 rather than out of 17,
because `grade_folder` runs `cbf_map_checks()` (10 checks, of which `3.4` is `N/A`
for an adult) rather than the whole registry — the fraction is what matters, not the
denominator.

| The folder has | What happens | How you find out |
|---|---|---|
| No CBF map at all | **silently skipped.** It does not appear in `subjects`, is not counted in `summary.total`, and produces no message. | Compare `len(subjects)` against the number of directories you expected. This is the failure mode to watch for. |
| CBF only | graded; every tissue-dependent check returns `UNKNOWN` | `coverage 1/9`, `complete=False`, `qei=None` |
| Tissue maps on a **different voxel grid** from the CBF map | `load_cbf_inputs` raises with an actionable message, `_find_cbf_inputs` catches it and **retries with the CBF map alone** | `PASS` at `coverage 1/9`, `inputs=['cbf', 'voxel_mm']`, and eight reasons that read *"needs CBF + GM mask"* — even though you supplied one |
| Tissue maps written **0–255** instead of 0–1 | identical: the loader raises, the exception is swallowed, the maps are dropped | identical — `PASS` at `coverage 1/9`, indistinguishable from the grid mismatch |

The last two are the sharp edge of batch mode, and worth stating plainly to a
reviewer. Both come back **`PASS`**, because the plausibility check `3.5.brain_cbf`
still grades the CBF map — so a cohort whose segmentations were all silently
dropped reports a 100% pass rate. Only the coverage column gives it away. And the
`except Exception` in `_find_cbf_inputs` throws away the *one* message that would
have told you what to fix —

```
gm shape (8, 8, 8) != cbf shape (36, 36, 28) — resample the tissue maps into ASL space first
gm is not a probability map: its maximum is 254.944, not <= 1. It looks like a 0-255
segmentation — divide by 255 before grading. …
```

— and reports *"needs CBF + GM mask"* instead. Until that is fixed, **verify a
tissue map on one subject through `load_cbf_inputs` directly before running the
cohort**, where the exception will reach you:

```python
from osipy_qc.io import load_cbf_inputs
load_cbf_inputs("cohort/sub-01/cbf.nii.gz",
                gm="cohort/sub-01/gm.nii.gz", wm="cohort/sub-01/wm.nii.gz")
```

**A cohort where every subject reports `coverage 1/9` almost always means one of
those two mistakes applied uniformly** — not that every scan is fine. Check the
coverage column before the pass rate, every time.

## 4. The dashboard needs a frontend build; the wheel does not carry one

The cohort dashboard is a React app in `web/`. Its build output, `web/dist`, is
git-ignored (matched by the root `.gitignore`'s `dist/`), so it is **absent from a
fresh clone**. Build it once:

```bash
npm --prefix web ci
npm --prefix web run build
```

Without it, `--dashboard` starts, grades the cohort, serves the API — and shows you
the wrong page. Verified with `web/dist` moved aside:

```
$ curl -s localhost:8745/ | grep -o "<title>[^<]*</title>"
<title>osipy-qc &mdash; ASL quality control</title>     # the UPLOAD console, not the dashboard
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:8745/overview
404
$ curl -s localhost:8745/api/cohort | python -c "import json,sys; print(json.load(sys.stdin)['total'])"
7                                                       # the data is all there
```

`_spa_root()` returns `None`, `_serve_spa()` declines, and the handler falls
through to the upload console. No warning is printed. If `--dashboard` looks like
the single-scan upload page, you have not run the npm build.

`--serve` is unaffected: it sets `spa=False` deliberately and renders its own HTML,
so the single-scan console works with no Node toolchain at all.

**A wheel can never carry the frontend.** `pyproject.toml` packages `osipy_qc*`
with `package-data = ["py.typed"]` only, and nothing copies `web/dist` into
`osipy_qc/webui`. Confirmed by building one:

```
$ pip wheel . --no-deps -w /tmp/w
$ python -c "import zipfile,glob; print([n for n in \
    zipfile.ZipFile(glob.glob('/tmp/w/*.whl')[0]).namelist() \
    if n.endswith(('.js','.css','.html'))])"
[]
```

So `_spa_root()`'s first candidate (`osipy_qc/webui`) is dead code today, and the
dashboard is a **source-checkout-only** feature. `pip install osipy-qc` gives you
the library, the CLI and `--serve`, but not the cohort UI.

## 5. Where `--help` and the behaviour disagree

| Flag | The mismatch |
|---|---|
| `--demo` | Says "the full **Stream B**"; runs the **whole registry**, so ten checks that cannot apply also run and report `UNKNOWN`. |
| `--population` | Validated only on the `--demo` / `folder` paths. `osipy-qc --dashboard X --population toddler` starts happily and grades against **adult** bands — verified, `/api/cohort` returns `"population": "adult"`. In single-scan mode the same value is a hard error: *unknown population 'toddler'; known: ['adult', 'neonate']*. So `--population neonate` is silently ignored for a whole neonatal cohort. |
| `--dashboard` | Says it will "serve it". It will serve the API, but renders the dashboard only if `web/dist` exists; otherwise you silently get the upload console (§4). |
| `--html` | Documented without a scope. It is ignored on the three server paths and on `--provenance`, because each returns before the HTML is written. |
| `--serve` | Says "upload a single CBF map". It also accepts raw acquisition files through the same form, and grades Stream A from them. |
| `--provenance` | Ends with *"Full write-up: THRESHOLD_PROVENANCE.md"*. **That file does not exist in the repo.** `report_html.py`, `README.md` and `USAGE.md` link it too, as they do the equally absent `POPULATION_BANDS.md`. |
| `--dashboard` on an empty folder | Not documented, and it matters for hosting: it calls `ap.error(...)`, which exits **2**. Verified. |

---

## 6. Why the cohort dashboard is not on the public instance

`render.yaml` runs `osipy-qc --serve`, the single-scan upload console — not
`--dashboard output`. Its own comments give two reasons, and both check out:

1. **It would crash-loop.** A clean checkout contains only `output/.gitkeep`, so
   `grade_folder("output")` finds no subject folder with a CBF map, `cli.py` calls
   `ap.error(...)`, and the process exits with status 2. A platform that restarts a
   web service whose start command exits non-zero would restart it forever.
   Verified:

   ```
   $ osipy-qc --dashboard /an/empty/dir --no-browser; echo "exit code = $?"
   osipy_qc: error: no subject folders with a CBF map found under '/an/empty/dir'
   exit code = 2
   ```

2. **It would publish participant data.** On the developer's machine `output/`
   holds CBF maps derived from the three mentor-provided datasets, including ADNI
   `027_S_6327` (§0). Serving `--dashboard output` at a public URL would put those
   scans, and the figures rendered from them, on the open internet. The folder is
   git-ignored precisely so it cannot reach the repository; pointing the public
   start command at it would defeat that.

There is a third, quieter reason worth knowing: the dashboard would not render
anyway unless the npm build ran (§4), and the free plan's cold start pays the full
cohort re-grade on the first request after it sleeps.

**The rule that follows:** `--dashboard` is a local tool. Run it on your own
machine, against your own cohort, on `127.0.0.1`. If you need to share a result,
share the self-contained HTML report (`--html`), which contains only what you chose
to put in it — and check its embedded figures before you send it, because they are
rendered from the scan.
